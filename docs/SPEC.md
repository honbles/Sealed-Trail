# Sealed Trail: Deployment Spec (greenfield build from paper v4)

**Basis.** The paper "Sealed Trail: A Cryptographically Verifiable Financial Provenance Network", Version 4 (2026), read in full. Nothing else is assumed to exist: no code, no earlier prototype, no earlier test results, no keys, no infrastructure. Every component below is built from scratch.

**Conventions.** "Paper §n", "Thm n", "Prop n", "Alg n", "Table n" refer to the paper. "§n" alone refers to this spec. Decision IDs `D1..D33` refer to the decision log in §9, where the paper is silent or inconsistent and this spec pins a choice.

---

## 0. Starting point, stack, repository

### 0.1 Starting point
Nothing exists. The first deliverables are the repository, the cryptographic core, the encoding, and conformance vectors (M0, §12). The paper's reported numbers (Tables 7 and 8) come from toy generators that must also be built, so they can be reproduced (T-TOY-7, T-TOY-8).

### 0.2 Stack decision
| Layer | Choice | Why |
|---|---|---|
| Crypto and protocol core (`st-crypto`, `st-core`) | Rust: `curve25519-dalek` (Ristretto255, for Pedersen), `bulletproofs` (published range proofs only, **no R1CS**), `merlin`, `ed25519-dalek`, `frost-ed25519` | The paper needs Pedersen commitments and aggregated Bulletproof range proofs. No mainstream Python library provides this. Pin exact versions at build time (§7.3) |
| Services (validator, bank, NA, TSA, TIV, oracle, regulator, review, registry, custody, observer) | Python (FastAPI) calling the Rust core through PyO3 | Fast to build and instrument. Validation logic lives in the core, so there is one `Valid(e)` |
| Taint engine, monitors, harness, shadow ledger, load generator, reports | Python with exact rationals (`fractions.Fraction`) | The shadow ledger must be an **independent plaintext implementation**, not a wrapper over the core |
| Orchestration | Docker Compose generated by a script | One command from a clean machine |

### 0.3 Repository layout

## 1. Purpose, pass criteria, non-goals

The deployment turns the paper's analytic model into evidence. It has five jobs:

1. **Conformance.** Every lemma, theorem, proposition and algorithm maps to an automated test (§10.1).
2. **Adversarial.** All 15 threat classes of Table 6 are exercised, including the classes the paper marks unprotected or boundary (§10.2).
3. **TIV and anchoring.** The partial-adoption claim (Table 1) and the escrow, clean-attestation and deferred-anchor machinery are exercised end to end with real TIV services (§6).
4. **Measurement.** The 10 planned measurements of paper §8 are produced with seeds and raw data (§10.4), plus the capacity costs (iv) and (v) of the paper's national-scale discussion (G1 growth, validator bootstrap).
5. **Reproduction of toy results.** Tables 7 and 8 regenerated by code that ships with the repository.

**Pass** = all P0 tests green; monitors M1 to M11 (§8.4) report zero violations across full runs; every measurement bundle is reproducible from `(git SHA, profile, seed)`.

**Non-goals** (paper open problems 1 to 6 and listed non-guarantees stay open): continuous exposure scoring across flags, bounding the UNRESOLVED set, zero-knowledge graph privacy and a privacy bound, collusion detection, multi-hop external recovery, validator reconfiguration, version pipelining, post-quantum commitments, and the national-scale event rate (analytic only; the deployment reports scaling curves).

### 2.3 Sizing (planning estimates, not measurements)
- RAM about 50 to 100 MB per idle container. The bottleneck is validator CPU: every validator verifies every event (aggregated range proof, zero-or-floor proofs, signatures, lock writes).
- Plan 16 to 32 GB RAM and 8 or more cores for the 100-bank run. Expect tens to low hundreds of events per second total. State this in every results bundle.
- Storage per validator at about 2 KB per event (paper estimate): 1M events is about 2 GB, plus the child index.
- Scale in steps: 5, 10, 20, 50, 100 banks. Each step passes the conformance suite before the next.

```
stctl up --runtime local --banks 20 --accounts-per-bank 10 \
         --validators 7 --byzantine 2 --na-signers 5 --na-threshold 3 \
         --tsa 3 --oracles 5 --tivs 3 --jurisdictions 2 --seed 42
make up BANKS=20 ACCOUNTS=10 VALIDATORS=7 RUNTIME=docker      # same thing
stctl scale banks 40        # onboard more banks into a running network
stctl scale accounts 25     # more accounts per bank (new GEN roots)
```
Banks and accounts can be added to a live network (onboarding). Validators and NA signers are fixed per run, because validator reconfiguration and re-keying are not specified in the paper.

**Three runtimes, one code base, one HTTP API:**

| Runtime | What it is | Use |
|---|---|---|
| `inproc` | All nodes as asyncio apps in one OS process, in-memory HTTP transport, deterministic `Clock` | Conformance suite, model checks, large sweeps. Thousands of nodes are feasible because a node is a lightweight object |
| `local` | One OS process per node, `uvicorn` on `127.0.0.1:<port>`, real HTTP | Simulation on any machine **without Docker**; realistic message paths |
| `docker` | One container per node from a single image, role selected by environment, compose file generated by `stctl` | Packaging, real `tc netem`, partitions via `docker network disconnect`, the 100-node run |

The transport layer carries a **network shim** (latency, jitter, loss, partition groups) used in `inproc` and `local`, so partition and latency tests run without Docker. Latency numbers from `inproc` are simulated, not network measurements, and every results bundle labels its runtime. Proof prove/verify timings come from the real Rust crypto and are only meaningful on the hardware they were run on.

**Accounts:** `--account-mode inproc|process`. Default `inproc` runs account agents as tasks inside `bank_app` so 100 banks × 10 accounts does not mean 1,000 processes. `process` gives each account its own node for small runs that stress the bank API.

**Identities and ports** are deterministic: `bank-0007`, `acct-0007-0003`, `val-03`, `na-2`, ports from a base. `stctl ceremony` generates keys and certificates for exactly the requested counts before start.

## 3. Services

Transport: HTTP, bodies `application/cbor` for events and JSON for control. Services use TLS with a **test transport CA** (X.509, Ed25519 or P-256 keys) generated by `stctl ceremony`: off in `inproc`, plain loopback HTTP in `local` unless `--tls`, on in `docker`. This is deployment plumbing, separate from the protocol: **protocol certificates** are CBOR objects signed by the NA that carry a `role` (`bank`, `validator`, `oracle`, `regulator`, `review`, `tsa`) and are checked inside the protocol, never by TLS (D32). TIVs sit outside this PKI (§6.2). All durable state in every service is SQLite (WAL). All services read time through a `Clock` abstraction so the harness can skew or accelerate it.

### 3.1 `validator_app`
**Durable state:** G1 events with certificates; `Lock: key → id`; `Hold: entry → set of flag ids`; children index; ordered index of anchors by (token time, depth, id); depth per event; E3 edges; flag log; opening log; CRL epoch log; per-flag cone sets.

**Lock step (Alg 2)**, one atomic critical section: check `Valid(e)`; reject if a parent entry is Held and the event is not a REV; reject if any key's lock is not in {⊥, id(e)} (D3); reject if some lock is ⊥ and `tnow − ttok > Δstale`; write all ⊥ locks; return the signature. The lock write must be **durable (fsync) before the signature leaves the process**, otherwise a crash makes the validator behave as Byzantine. Re-sign when every key is already locked to id(e), whatever the token age.

**Store (D33).** SQLite, WAL mode, `PRAGMA synchronous=FULL`, one file per validator, **one writer**: one process, `workers=1`, one writer task that owns every write transaction (the process refuses to start with more than one worker, since a multi-worker server would break the atomicity). The lock step is a single `BEGIN IMMEDIATE` transaction: read lock and Hold rows, check, write lock rows (primary key = lock key), `COMMIT`; the signature is produced and returned only after `COMMIT` returns. Concurrent requests are group-committed (one transaction and one fsync per batch, processed in order, so a later request in the batch sees an earlier one's locks). Proof verification runs before the transaction in a worker pool (PyO3 releases the GIL), so the writer only does key checks and inserts. Readers use separate read-only connections. `inproc` uses in-memory SQLite (same code path, not crash-safe); crash tests run in `local` or `docker`. Tables: `events, certs, locks, children, anchors, holds, cones, e3, flaglog, openings, crl_epochs`.

**Keys:** `(p, v)` for a debit, EXT or REV; `rid` for a GEN; `(TIV, ν)` for an ANC.

| Endpoint | Purpose |
|---|---|
| `POST /v1/lock` | CBOR event; returns σv(id) or a reason code |
| `POST /v1/finalize` | Q(e); validator verifies q signatures, marks Finalized, updates child index, depth, E3, cone (ONLEARN) |
| `GET /v1/events/{id}`, `GET /v1/entries/{id}/{j}` | Event; or owner, currency, κ, finalized version count, Held flag |
| `GET /v1/children/{id}/{j}` | Child index |
| `GET /v1/sync?cursor=` | Replica and peer sync (parent- and version-closed) |
| `POST /v1/abort/statement`, `POST /v1/abort/apply` | Abort proofs (k+f−q+1 statements; apply resets keys locked to a never-finalizable event) |
| `POST /v1/flags`, `GET /v1/flaglog` | Flag and RELEASE artifacts; log replayed before signing anything after join or recovery |
| `POST /v1/openings`, `GET /v1/openings` | Opening accepted iff Com(a;r) matches the public or derived commitment; reads need regulator credentials |
| `GET /metrics`, `GET /v1/g1/stats` | Observability |

On a missing parent or earlier version, fetch from peers before judging validity (Cor 10). A validator that joins or recovers replays the flag log before it signs.

### 3.2 `bank_app`
**State:** customers and wallets; wallet-to-entry share map (private); per entry `(κ, a, r)` and residual blinding `r_res = r − Σ r^c`; **openings and ρ of every event issued or received**, kept as long as a flag could name an ancestor; settlement advice; delivery inbox; local G1 replica.

**Functions**
- *Payment constructor:* pluggable parent selection (FIFO, LIFO, random, adversarial steering), dust-aware subset search (Prop 20), multi-output batch builder (one payroll run is one event), re-homing, consolidation, wallet-granular entry mode.
- *Event builder:* fresh blindings for consumed portions; output blindings chosen so Σrj = Σr^c (r* = 0); aggregated range proof; zero-or-floor proof per parent; settlement-advice hashes `hj = H(advice ‖ salt)`; Travel Rule bundle hash above the FATF threshold (bundle travels bilaterally); signature over id(e).
- *Finality client:* send to all k validators within Δstale, assemble Q(e), post `/v1/finalize`, wait for finality before using version v+1 of the same entry. **A bank never acts on an unfinalized event** (Prop 11 interface contract); a test profile acts early to show the exposure.
- *Delivery:* after finality, send each receiving bank `{event_id, j, a, r, ρ, advice, salt}`. The receiver checks Com(a;r)=κj, `hj`, and that advised amounts sum to a. On a mismatch it rejects and returns the value with a new debit.
- *Anchoring:* requests TIV attestation for inbound external value (§6).
- *Flag handling:* watch the flag log; open consumed portions of cone events it issued and residuals of cone entries it owns (Phase 2); compute Tb; issue REV(mb) per policy (Phase 3).
- *Reconciliation job:* customer balances against the sum of owned residuals. The network cannot check this (Table 3), so it is a local monitor (M8).

**Behaviour profiles** (config flags, not code forks): `honest, refuse_open, lie_open, refuse_rev, declare_exhausted, equivocate, steer, poison, fabricate, stale_submit, misreport_custody, act_unfinalized`.

### 3.3 `na_*` (reserve attestation, certificates, CRL, CT log)
- (τ, nNA) = (3, 5). Feldman-VSS distributed key generation; FROST(Ed25519, SHA-512) threshold Schnorr signing (RFC 9591), so every NA, regulator and review-body threshold signature verifies as a plain Ed25519 signature (D32).
- Issues certificates with a `role` for banks, validators, oracles, regulators, review body, TSAs. Registers regulators (treg-of-nreg, scope J, recognition set MJ) and the review body.
- Issues reserve attestations `(rid, C, Amax)`, each `rid` fresh. **Policy: attest only at onboarding, one attestation per account** (D17). The network cannot enforce "GEN only at onboarding" because V5 contains no such rule, so the NA service enforces it and logs every attestation in the CT log.
- CRL: versioned sparse Merkle tree, signed root per epoch, O(log n) non-membership proofs.
- Revokes a bank certificate on a regulator's request (non-compliance path).

### 3.4 `tsa_app`
RFC 3161 tokens whose message imprint is id(e). A token is valid only when mt of nt authorities sign and their clocks agree within δskew. Test mode: per-TSA offset and rate; key revocation time `trev`.

### 3.5 `oracle_app`
Each oracle signs `(pair, value, t)`. A rate document `{pair, ε=(εn, εd) in lowest terms, tε, observations[(oracle_id, value, σo)]}` publishes the **lower median**. Anyone may assemble it. Validators recompute the median and verify every σo, so the aggregator is untrusted. Test mode: oracles with lie offsets.

### 3.6 `tiv_app`
Full specification in §6. In short: signs anchors, optionally attests clean (with liability), holds a nonce counter, consults the external-world evidence ledger.

### 3.7 `registry_app`
Bank, TIV and validator ids to endpoint, certificate, jurisdiction. Fed from NA-issued certificates. No ledger data (owners are already public in G1).

### 3.8 `custody_app`, `observer_app`
`observer_app` is a read-only replica. `custody_app` builds the public **unweighted** G3 from G1 only:
- `GET /g3/edges`: the E3 multigraph, one tuple per inter-bank output, plus `(b, ⊥, t)` per EXT and `(⊥, b, t)` per ANC.
- `GET /g3/reach`: simple projection, at most n(n−1) edges.
- `GET /g3/gamma`: γ per Prop 17 with the definition pinned in D9.

It never serves mass. Before any flag exists there is no mass data to serve, by design (Cor 16).

### 3.9 `regulator_app`
- Threshold flag signing (treg-of-nreg), scope J, recognition set MJ, recovery bank `brec` (must be in J ∪ MJ, D16).
- Flag builder: root set Kφ with injections xφ; oracle-fraud flags using the contributor index (every international debit whose rate document contains σo with a timestamp in `[t1, t2]`) and the true rate ε*.
- Orchestrates Alg 3: Phase 1 (pruned temporal walk and CONEBUILD over a replica, B1), Phase 2 (collect, verify and mirror openings), Resolve (Alg 4), Phase 3 calls, Phase 4 annotation and release artifact.
- **Taint engine** and policy (§8). The weighted G3 per flag lives here, fed by the opening log mirrored from validators. Regulator-only API.
- Reports: `ExposureReport(F)` listing B1 \ (J ∪ MJ); non-compliance record; TotalContamination, BanksAffected, RecoveryRate; annotation of cone entries with ρ > 0 by ⌈log2(1/ρ)⌉ (regulator view only).
- Policy plug-ins: `Policy(Tb) → mb` (full, fixed fraction, none), `actors.json` (bank sets per actor for TA and Tmin), good-faith exemption hook (affects mb only, never Hold), steering analysis (compare each bank's outbound mass share on cone debits against its pro-rata average).

### 3.10 `review_app`
Signs RELEASE artifacts. Signer set disjoint from every regulator's. Keys in separate containers.

### 3.11 `loadgen`, `harness`
See §11.

## 4. Wire format and pinned encodings

**Event types:** `GEN, DEB, ANC, EXT, REV`. REV carries `rev_kind ∈ {reversal, restitution}` (D2).

**Entry identifier:** `(id(e), j)`. **Parent triple:** `(p, vp, κc_p)` with `p = (id, j)`.

**Preimage `Enc(e)`** = `tag_type ‖ CBOR_det(body)`. Body: type, rev_kind, issuer, outputs `[(owner, currency, κj, hj)]`, parents, `ep(e)` (CRL epoch), international fields `(εn, εd, oracle_id, tε, θ)` when applicable, `rid` or `(TIV, ν, clean)`, flag reference for REV, Travel Rule hash. **Excluded:** range proofs, zero-or-floor proofs, RFC 3161 token, issuer signature, certificate Q(e) (D1). The token's imprint is id(e), so it cannot sit inside the preimage; proofs are checked against commitments, so any valid proof is acceptable.

**Strict decoding:** reject duplicate map keys, non-shortest integers, indefinite lengths, trailing bytes.

**Aggregated range proof:** one proof over the ℓ output commitments, the P consumed-portion commitments and the P floor commitments `Cx − ωC·Cz` (below), plus limb commitments for V4 (§7.1). Outputs prove `a_j − ωC ∈ [0, 2^64)` (D4). Padding to a power of two uses identity commitments, defined deterministically.

**Zero-or-floor proof** per parent (D30): a commitment `Cz = Com(z; rz)` to a selector bit and a sigma-OR proof (§7.1); the commitment `Cx − ωC·Cz` is one more party in the aggregated range proof.

**ANC TIV-signed tuple:** `(issuer, κe, ν, clean)` (D15).

**Flag** `F = (Kφ, xφ per root, J, tflag, texp, nonce)` + treg-of-nreg signature. **RELEASE:** flag id + review-body signature. **PHASE4(φ):** regulator-signed list of banks below Tmin (D6). **Opening record:** `(commitment ref, a, r)`, never in G1.

## 5. Protocol flows

### 5.1 Onboarding
Per account: NA threshold-signs `(rid, C, Amax)`; the bank builds a GEN with one output and the cap proof `Com(Amax; 0) − κe ∈ [0, 2^64)`; validators lock `rid`. One GEN per account keeps later holds account-sized instead of bank-wide (S-GEN-POOL shows the contrast).

### 5.2 Debit
1. Select parents and amounts (dust-aware).
2. Draw blindings; build outputs and proofs.
3. Get an mt-of-nt time-stamp token. `ttok(e)` must be ≥ the token time of each parent's creating event (V1).
4. Sign id(e); send to all k validators.
5. Collect q signatures; post `/v1/finalize`.
6. Deliver openings, ρ and settlement advice to receiving banks.
7. Receivers verify and credit.

Customer payments inside one bank are not network events; they reassign shares in the bank. Re-homing is the exception: an ordinary debit whose outputs belong to the issuer.

### 5.3 International debit
Rate document from the aggregator; V4 tolerance proofs on `θ·ε·Σκc ± κΔ` (width problem in §7.3).

### 5.4 Anchors and exits
Full flow in §6. EXT carries the committed exit amount κx and no output entry.

### 5.5 Flag, hold, reverse (Alg 3)

| Phase | Actor | Behaviour | Deadline |
|---|---|---|---|
| 0 Hold | Validators on receipt of F | CONEBUILD over the child index **plus the anchor-window rule** (from every EXT in the cone, every ANC within Wesc after it, because amounts are hidden and no validator can tell which anchors will draw taint; D27); Hold the outputs owned by banks in J ∪ MJ (all cone outputs, since a zero residual looks live, D20); refuse locks with a Held parent except REV; ONLEARN extends the hold to late descendants and late anchors | Thold |
| 1 Exposure | Regulator, from G1 | Pruned temporal walk, then causal CONEBUILD; B1 = owners of live cone entries; foreign owners reported, not held | |
| 2 Open | Banks in B1 ∩ (J ∪ MJ) | Open consumed portions of cone events they issued, residuals of cone entries they own, and the output commitments of cone roots **and cone anchors** they own (D28); regulator and validators accept iff the opening matches | Topen |
| Resolve | Regulator, validators | Alg 4 in (token time, depth, id) order; UNRESOLVED is viral | |
| 3 Reverse | Banks with no UNRESOLVED ancestor and TA(b) ≥ Tmin | Policy gives mb; bank issues REV(mb) | Trev |
| 4 Release | Validators | Release resolved Held entries with ρ = 0 (anchors that drew nothing), whatever their bank's Tb; release Held entries of banks that issued REV and of banks in `PHASE4`; UNRESOLVED stays Held until texp | |

Expiry at texp lifts the flag by default. RELEASE lifts it early. Banks that do not open or do not issue REV are not compelled: entries stay Held, the NA may revoke the certificate on request, and a non-compliance record is emitted.

### 5.6 REV and restitution
`REV(m)` of bank b: parents are Held cone entries of b in the cone of Kφ, Σcp = m, one output of amount m owned by `brec` with ρ = 1; settlement factor λ is computed from the Phase 2 openings and stored with the event. m follows Prop 20 rounding (least feasible m′ ≥ m if m′ ≤ Tb, else greatest feasible m′ ≤ m; never m′ < ωC). **Restitution:** `rev_kind = restitution`, issued by `brec`, consumes a recovery entry, output owned by the beneficiary, ρ = 0, no λ. Recovery entries stay Held until restitution or texp (D7).

### 5.7 Lock recovery
Idempotent re-signing first; otherwise an abort proof. Keys of equivocating owners stay locked (validator reconfiguration is not specified).

## 6. TIVs, anchors, escrow

### 6.1 Roles
The paper leaves the TIV for each category open and calls it a deployment choice. This build fixes defaults and keeps them configurable.

| Outside-value category (paper §2) | Default TIV | Natural real-world candidate |
|---|---|---|
| Cash deposited at a branch or agent | `tiv_cash` | Independent settlement agent or supervisor |
| Inbound transfer from a bank not on the network | `tiv_inbound` | Correspondent or settlement agent |
| Settlement arriving over an external rail; re-entry of value that earlier left through EXT | `tiv_rail` | Supervisor or rail operator |

Three TIVs let liability attribution be tested per TIV. Where a country already runs a system that attests such value, that system is the TIV; the protocol only needs its public key.

### 6.2 Identity and trust
- A TIV is a trusted external party. There is no registration protocol, no NA certificate and no CRL check for TIVs (D15a). Validators hold a **static trust list of TIV public keys** from deployment config (in a real deployment, whatever national system already attests such value).
- Validators check the ANC signature against that list. The list is disjoint from bank keys, so **a bank cannot be its own TIV**; this is a configuration constraint, not a protocol rule.
- The TIV learns the amount by opening `(a, r)` of κe and is trusted for it (Table 6, row 1).

### 6.3 Anchor flow
1. External value arrives (simulated by `external_world`, which records the evidence).
2. The bank draws `(a, r)`, forms κe, and sends the opening to the TIV over the transport channel.
3. The TIV checks the evidence ledger (honest profile) and signs `(issuer, κe, ν, clean)`.
4. The bank builds the ANC with one output, a range proof, and the TIV signature, and sends it to validators.
5. Validators lock `(TIV, ν)` and verify the signature; one signed commitment cannot be anchored twice (Thm 6, Prop 7).

**Nonce ν** is unique per TIV: `ν = (tiv_id, 64-bit counter)`, persisted before signing. A reused ν only produces a conflict that the lock resolves.

### 6.4 Escrow rules (implemented in the engine, §8.2)
- EXT appends a tranche `(token time, Σρcp)` to the per-flag, per-currency escrow Eφ.
- An unattested ANC of amount A gets ρ = g/A with g = min(A, Eφ), drawing g from the **oldest tranches first** (D25). An ANC named by the flag as a root gets ρ = 1.
- If the anchor carries c = 1 (clean), ρ = 0 and the TIV records a contingent liability of min(A, Eφ). **Eφ is left untouched** (D26): the mass stays in Eφ until it expires into Zφ.
- **Anchor-window rule (hold).** The cone is closed under two steps: event to children, and from an EXT in the cone to every ANC within Wesc of it, before or after (two-sided, so an anchor that entered clean before the exit is visible to the deferred-anchor rule). Validators hold all of those anchors until resolution; at Phase 4 the ones that drew nothing (ρ = 0) are released (D27).
- The unmatched part ua = A − min(A, Eφ(t)) of an unattested anchor that entered clean stays **open for Wesc**. If a later EXT adds mass M to Eφ inside that window, min(M, Σua) moves from Eφ to a claim Yφ against the TIV, oldest open anchors first, closing those ua. No entry's ρ is revised.
- {EXT, ANC} events are processed in order of (token time, depth, id); depth is 0 for ANC.
- Escrow older than Wesc moves to Zφ (written off). Restitution moves mass to Dφ.
- Matching is by amount and time, not identity: an unattested anchor receives taint even when unrelated to the flag. The remedy is a clean attestation, at the TIV's liability.
- TIV liability arises in exactly two ways: a clean attestation signed while Eφ > 0, and the deferred-anchor rule.
- Anchors with ρ > 0 are extra roots of the flag that do not enlarge Pφ.

### 6.5 Batching
A deployment may batch deposits into periodic anchors (one ANC per interval per TIV). Latency rises, signature count falls. Batched anchors coarsen the time used for escrow matching; the effect is measured (T-TIV-9).

### 6.6 Not covered by the paper (documented, not solved)
- A flag that names an anchor directly taints it whole (ρ = 1) and attaches **no** TIV liability.
- TIV liability is recorded as a claim (Yφ and per-TIV clean-attestation claims). The protocol has no collection mechanism; recovery is legal or supervisory.
- **No mint ceiling on ANC.** Genesis is capped by Amax; anchors are capped by nothing but the TIV's signature. A dishonest TIV can mint without bound. Lemma 5's "a bank cannot mint after genesis" is about banks only; the sentence after it is reworded in the paper to say anchored value is bounded only by the TIV's signature. M11 publishes a per-TIV anchored-supply commitment (Σκe over that TIV's anchors) that the TIV can open on audit; this is a monitor, not a protocol rule.
- A GEN after onboarding would let exited value re-enter clean. Prevention is NA policy (§3.3), not network-verifiable.
- **Over-hold.** After a flagged exit every in-scope anchor of the next Wesc is held until resolution, related or not (the paper lists this as a limitation). A party that can cause a flagged exit can briefly freeze unrelated inflows; if an opening is refused the freeze lasts until texp.
- **Refusal and the window.** An Unresolved exit or anchor leaves later exits and anchors in its window Unresolved, so a refusal, or an exit by a bank outside J ∪ MJ, can keep in-scope anchors Held until texp.

## 7. Crypto build plan

### 7.1 Primitives
- Pedersen commitments over Ristretto255; `g` standard, `h` = hash-to-group of the fixed string `sealed-trail/h/v1`. Range proofs use the same `(g, h)`.
- Range proofs: only the published `bulletproofs` `RangeProof` (aggregated, 64-bit, party count padded to a power of two). Its R1CS API sits behind the `yoloproofs` feature, is labelled experiments-only and is disabled in the published release, so **nothing in this build uses it** (D30).
- **Zero-or-floor proof (D30), no circuit.** For each parent, `Cx` is the derived residual commitment. The prover adds `Cz = Com(z; rz)` with z = 1 iff the new residual is ≥ ωC, and proves, with a Fiat-Shamir sigma-OR (merlin transcript), knowledge of the discrete log base `h` of either (A) `Cz − g` [z = 1], or (B) both `Cz` and `Cx` [z = 0 and x = 0]. Separately, `Cx − ωC·Cz` is a Pedersen commitment to `x − zωC` and joins the event's aggregated range proof. If z = 1 the range proof gives x ≥ ωC (with the D4 shift); if z = 0 branch B forces x = 0. Size is about `Cz` + 3 points + 4 scalars per parent (about 0.25 KB, to be measured) plus one aggregate party.
- **Wide values for V4 (D31), no circuit.** A tolerance value below 2^213 is split into limbs of 64, 64, 64 and 32 bits (224 bits in total, below the group order of about 2^252, so no wrap). The prover commits to each limb with blindings chosen so `C_v = Σ 2^(64i)·C_limb_i`, and each limb is a party in the aggregated range proof.
- Signatures: Ed25519 for banks, validators, TIVs, oracles, TSAs. FROST(Ed25519) for NA, regulators and the review body. SHA-256 for ids.
- Narrow interface between `st-crypto` and everything else: `commit`, `open`, `prove_aggregate`, `verify_aggregate`, `prove_zero_or_floor` (OR proof plus the extra aggregate party), `verify_zero_or_floor`, `limb_commit`, `frost_*`.

### 7.2 Conformance vectors
Generated once from `st-core`, then used by every service build and by the independent shadow implementation: commitments, residual derivation, id computation, valid and invalid proofs (including OR-proof and limb vectors), median, λ, ρ.

### 7.3 Known implementation risks
1. **The sigma-OR is custom code.** It follows the standard Cramer-Damgård-Schoenmakers OR composition and is short, but no audited library supplies it. Mitigation: fixed domain separation per statement, vectors, negative tests (T-OR-1), and an external review before any claim of soundness beyond "implemented as specified".
2. **Proof size and cost** of the zero-or-floor and limb parties are estimates until measurement 1. The paper's 0.7 to 0.8 KB figure assumed a circuit and no longer applies; the aggregate now has ℓ + 2P parties plus limbs for international events.
3. **Aggregation needs a power-of-two party count**: padding rule in §4.
4. **No-wrap check at startup:** group order > 2^85 and Pmax, Mmax imply no sum reaches 2^84 (V3); limb total 2^224 stays below the group order.
5. **Toolchain.** My sandbox has no Rust installed; apt offers rustc 1.75, which may be too old for the newest crates. Pin crate versions with a compatible MSRV (check `frost-ed25519` first) or build on your machine. Timings are only meaningful where the Rust core runs.

## 8. Taint engine, policy, metrics, monitors

### 8.1 Arithmetic
Exact rationals only; no floats. ρ, λ, mass and Tb are `Fraction`s.

### 8.2 Engine (regulator-side, event-sourced)
- ρ(e, j) = ρ̂(e) + xφ(e, j)/Ae,j with ρ̂ pooled by consumed portions (Def 12); every output of a debit gets the same ρ̂.
- Root rules: flagged GEN has xφ = Ag; oracle-fraud root has xφ = min(max(0, Ar − ε*As), (1 − ρ̂)Ar), allocated pro rata over outputs; any other named root is flagged whole. The engine checks each flag's injections against the openings (D21).
- Exceptions to the pooled rule: REV output ρ = 1; restitution output ρ = 0 (D10).
- λ = (Tb − m)/(Tb − Σρcp), λ := 0 when m = Tb; applies to every cone entry of b from the REV onward.
- Resolve (Alg 4) walks the cone in (token time, depth, id) order with two queues: escrow tranches and open anchors `(anchor, ua, time)`. Tranches and open anchors older than Wesc at the current token time leave the queues, tranches into Zφ. An EXT appends a tranche and moves min(M, Σua) to Yφ, closing open anchors oldest first; an unattested ANC draws from the oldest tranches. Rules in §6.4.
- An Unresolved {EXT, ANC} makes every later {EXT, ANC} within Wesc Unresolved (D29), including events of banks outside J ∪ MJ.
- Cross-currency: Thm 14 is stated for single-currency cones; the five-term identity is tested per currency on such cones, and for converted mass only the θ-per-hop deviation is checked (D14).
- Pro-rata is the only tracing rule implemented; the tracing rule is a parameter in the paper, so the engine isolates it behind one interface (FIFO and lowest-intermediate-balance are stretch work).

### 8.3 Metrics
TotalContamination = Σb Tb; BanksAffected = |{b : Tb > 0}|; RecoveryRate(φ) = (Σ over brec of ρR + Dφ)/Pφ; `1 − RecoveryRate` = (Σ other ρR + Eφ + Yφ + Zφ)/Pφ.

## 11. Harness, fault injection, reproducibility

### 11.1 Orchestration
`stctl up` takes the flags of §2.4. For `--runtime docker` it first runs `generate_compose.py` with the same flags, which writes `docker-compose.yml` (one service per node, one image, role by environment); for `local` and `inproc` it starts the nodes directly.

`stctl`: `up`, `down`, `ceremony` (DKG for NA, regulators, review body, TSAs; issues certificates), `scenario run <ID>`, `partition <A|B>`, `chaos <profile>`, `timewarp <rate>`, `report`.

### 11.2 Shadow ledger and external world
- **Shadow ledger:** records every submitted event's plaintext through a side channel and independently computes balances, residuals, cones, ρ, Tb and escrow state. It is a separate implementation sharing only the conformance vectors. Used for M9, M10, differential testing of the engine, and ground truth in adversarial runs. Never present in a non-test profile.
- **External world (⊥):** evidence ledger of deposits, inbound transfers, rail settlements and exits that TIVs consult; includes a mode where evidence is missing.

### 11.3 Workload mixes
Parameters: customer payments inside a bank (no network event), inter-bank single-output debits, payroll multi-output, re-homing, international, ANC by each TIV role, EXT. Controls: η target, parent-count distribution, hot-account skew (Zipf), fan-out. Fixed seeds; mixes named and versioned.

### 11.4 Fault injection
- Network: `docker network disconnect/connect`, `tc netem` (delay, loss, jitter; needs `NET_ADMIN`).
- Process: kill and restart validators mid-lock (checks durable lock-before-sign); kill a bank mid-event.
- Byzantine validators: sign two events on one key, sign nothing, delay. Up to f for protected tests, f+1 for the documented-void test.
- Time: per-TSA offset and rate; per-validator `Clock` skew; accelerated Wesc and texp.
- Bank and TIV behaviour profiles.

### 11.5 Reproducibility and observability
Pinned image digests, vendored Rust crates, seeded RNGs, git SHA and params in every bundle. Prometheus metrics; structured JSON logs with `event_id` and `flag_id` correlation ids.

## 13. Assumptions made (change any of these)

2. Default profile k=7, f=2, q=5; `k5f1` and `k5f0` kept for the paper's partition examples.

6. Single-flag behaviour is the claimed scope; overlapping flags are a stretch test.
7. No R1CS anywhere: zero-or-floor uses a sigma-OR and V4 wide values use limbs (D30, D31).
8. The external world is simulated; no real deposits, rails or banks are involved.
9. TIVs are trusted external parties configured as a static key list; there is no TIV registration protocol.
